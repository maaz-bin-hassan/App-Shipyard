# AGENTS.md

App Shipyard is an open-source starter kit that lets a developer pick one mobile platform and run the same slash commands in Claude Code, Cursor, OpenCode, Google Antigravity, or Codex. This repository defines the command format, the platform contract, the compiler, and the `createshipyard` CLI. The CLI copies one platform template into a new app.

Read [docs/SPEC.md](docs/SPEC.md) before editing anything under `commands/` or `platforms/`.

## Layout

```text
commands/<name>/COMMAND.md              platform-neutral Goal, Ask, Verify, Never
platforms/<id>/platform.json            manifest
platforms/<id>/fragments/<name>.md      Preconditions, Steps, Rollback
scripts/lint-commands.mjs               contract check
scripts/compile-commands.mjs            merges one platform into agent command files
scripts/sync-project.mjs                copies one template into a new app and compiles commands there
cli/                                    createshipyard, the TypeScript scaffolder
docs/SPEC.md                            command format, schemas, and design rules
docs/migrations/<version>.md            kit upgrade guides
.shipkit/state.json                     local run state, gitignored
```

Platform ids are `expo`, `flutter`, `android`, and `ios`. Generated command files are named `ship-<name>` and are gitignored. Edit the source files, then compile.

## Design rules

1. Idempotent and resumable. Skip a step already marked `done` for the current `kitVersion`.
2. Ask once in one batch. Ask every question in Ask before Steps, then reuse `.shipkit/state.json` `answers`.
3. Verify each step. Do not mark a step `done` without checking its result.
4. Secrets only in `.env`, and never printed. Do not write them into state, manifests, or the chat transcript.
5. Human gate before anything that spends money or publishes. Stop and wait for an explicit yes.
6. Minimal diffs. Touch only the files the current step names.

## State

`.shipkit/state.json` holds `platform`, `storeTargets`, `kitVersion`, `answers`, and per-command plus per-step `status` and `updatedAt`. The schema and the update procedure are in [docs/SPEC.md](docs/SPEC.md).

Create the file from that schema when it is missing. Write two-space JSON. Update only the command and steps this run touched. A changed `kitVersion` means previous `done` steps must run again.

## Goal

Ask which platform this project ships, save the app identity and store targets, compile only that platform's commands, copy its template and the shared backend, then run env-check and leave auth as the next command.

## Preconditions

- Ask has selected a platform, or `.shipkit/state.json` already has one.
- This fragment runs when that platform is `flutter`.
- `platforms/flutter/platform.json` exists. Store targets are `play`, `appstore`, or both.
- `platforms/flutter/template/README.md` is the stub template.
- Run every command from the repository root.

## Ask

Ask the platform question first, before any other question and before Steps. Ask it only when `.shipkit/state.json` is missing or `platform` is null. When `createshipyard` has already written `platform` as `expo`, `flutter`, `android`, or `ios`, skip this question and keep that value.

The platform choices are:

1. Flutter (`flutter`)
2. React Native (Expo) (`expo`)
3. Android native (Kotlin and Compose) (`android`)
4. iOS native (Swift and SwiftUI) (`ios`)

If the developer chooses `ios`, run `node -p process.platform`. When the output is not `darwin`, tell them iOS native requires macOS and Xcode, and ask again with only Flutter, React Native (Expo), and Android native. Do not save `ios` on that machine. If `platform` is already `ios` and the machine is not a Mac, stop, explain the same limit, and offer those three platforms before changing `platform`.

Then ask the rest in one batch. On resume, reuse `answers` and do not ask again.

| Id | Question | Record |
| --- | --- | --- |
| `appName` | App name | Non-empty string. |
| `applicationId` | Package or bundle id | Reverse-DNS string, such as `com.example.app`. |
| `primaryColor` | Primary colour | `#` plus six hex digits. |
| `languages` | Languages wanted | Array of language tags, such as `en`. |
| `storeTargets` | Store targets | Subset of the chosen platform's `storeTargets`. |

Offer only stores that platform lists. `expo` and `flutter` may be Google Play (`play`), the Apple App Store (`appstore`), or both. `android` offers only `play`. `ios` offers only `appstore`.

A blank required answer stays in this batch until it is filled. Do not start Steps with an empty name, id, colour, language list, or store list.

## Steps

1. Read `.shipkit/state.json`. If it is missing, create it with `platform` null, `storeTargets` [], `kitVersion` copied from `package.json` `version`, `answers` {}, and `commands` {}. If step `1` is already `done` for that `kitVersion`, leave it and continue. Otherwise record step `1` as `done`.
2. Skip when step `2` is `done` or `skipped` and `kitVersion` matches. Let `<id>` be the platform from Ask, or the saved `platform` when that question was skipped. If `<id>` is not `flutter`, do not write `flutter`. Run `npm run compile -- --platform <id>` and follow `platforms/<id>/fragments/start.md` from step 2 with the answers already collected. Stop this fragment. If `<id>` is `flutter`, record step `2` as `skipped`.
3. Skip when step `3` is `done` and `kitVersion` matches. Write `platform` `flutter`, `storeTargets` from the answers, and `answers` for `appName`, `applicationId`, `primaryColor`, `languages`, and `storeTargets`. Set `kitVersion` from `package.json`. Set `commands.start.status` to `in_progress`, record step `3` as `done`, and write UTC timestamps. Keep `storeTargets` inside `play` and `appstore`.
4. Skip when step `4` is `done` or `skipped` and `kitVersion` matches. If `platforms/flutter/platform.json` exists, run `npm run compile -- --platform flutter`. Confirm the generated `ship-*` files and `ship-*` skill directories are `ship-start`, `ship-env-check`, `ship-plan-pricing`, `ship-paywall`, `ship-analytics`, `ship-ai`, `ship-design`, `ship-translate`, `ship-legal`, `ship-publish`, and `ship-update`, and nothing else. Record step `4` as `done` when those names are the only generated commands. If the compiler fails or an extra `ship-*` command remains, record step `4` as `blocked` and stop. If `platforms/flutter/platform.json` is missing and `docs/kit/platform.json` exists, `createshipyard` already compiled those commands. Confirm the same names are present, record step `4` as `skipped`, and continue. If neither manifest exists, record step `4` as `blocked` and stop.
5. Skip when step `5` is `done` or `skipped` and `kitVersion` matches. If `platforms/flutter/template` exists, copy each file under it to the same relative path at the project root when that destination is missing. Leave an existing file as it is. In each file this step copied, replace `{{appName}}`, `{{applicationId}}`, and `{{primaryColor}}`. Copy `backend/` to the project root only when `backend/` is missing. If `platforms/flutter/template` is missing, leave the files `createshipyard` already wrote. Search the files this step copied, or `README.md` when it copied none. Record step `5` as `blocked` when `{{appName}}`, `{{applicationId}}`, or `{{primaryColor}}` remains. Otherwise record step `5` as `done`.
6. Skip when step `6` is `done` and `kitVersion` matches. Run env-check for flutter and write its state before continuing. Record step `6` as `done` when `commands.env-check.status` is `done`, and `blocked` when env-check is `blocked`.
7. Skip when step `7` is `done` and `kitVersion` matches. When step `6` is `done`, set `commands.auth` to `pending` with an empty `steps` object and the current UTC timestamp, set `commands.start.status` to `done`, and say that auth is next and has no command yet. When step `6` is `blocked`, set `commands.start.status` to `blocked` and leave `commands.auth` unset.

## Verify

`.shipkit/state.json` has the chosen `platform`, a `storeTargets` list inside that platform's manifest, and `answers` for `appName`, `applicationId`, `primaryColor`, and `languages`. Generated `ship-*` commands match that platform's `commands` and no other platform's generated commands remain. Template files that were copied have the three placeholders replaced. `commands.env-check` has a status. `commands.auth` is `pending` only after env-check is `done`. The state file and the transcript contain no secrets.

## Rollback

Set `commands.start.status` to `blocked` and timestamp it. Leave copied template files and `backend/` in place. Do not uninstall tools. Do not delete `.shipkit/state.json`.

## Never

Do not ask the platform question when `platform` is already set, except to leave an `ios` value that cannot be built on this machine. Do not save `ios` unless `node -p process.platform` prints `darwin`. Do not offer a store the manifest omits. Do not install, upgrade, or remove a toolchain unless the developer explicitly agrees after a failed env-check. Do not create accounts, spend money, upload a binary, or submit to a store. Do not print `.env` or secret files. Do not run auth. Do not mark start `done` while env-check is `blocked` or `pending`.

## Goal

Report pass or fail for every toolchain check in the selected platform manifest, print the install hint for this operating system when a check fails, and record the result in `.shipkit/state.json`.

## Preconditions

- `.shipkit/state.json` exists and `platform` is `flutter`.
- The manifest is `platforms/flutter/platform.json` in this repository. In an app created by `createshipyard`, it is `docs/kit/platform.json`. Use the first of those that exists.
- That manifest's `envChecks` name Flutter 3.47.0, Dart 3.13.0, JDK 17, Android SDK Platform-Tools, and an installed Android SDK platform (the manifest names Platform 36).
- Run every command from the repository root.
- This command only updates `.shipkit/state.json`. Application source is left untouched.

## Ask

No platform or store questions. Read `platform` and `storeTargets` from `.shipkit/state.json`.

The checks come first. If every check passes or is skipped, ask nothing and leave `answers.runInstallHints` unset. If any check fails and `answers.runInstallHints` is missing, ask once: may those install hints be run? Record `yes` or `no`. Wait for an explicit yes before running a hint. A refusal is `no` and leaves the command `blocked`. On resume, reuse `answers.runInstallHints` and do not ask again.

## Steps

1. Read `.shipkit/state.json` and `package.json`. If `commands.env-check.status` is `done` and `kitVersion` matches `package.json` `version`, report that the check already passed and stop. Otherwise record step `1` as `done`.
2. Set `commands.env-check` and step `2` to `in_progress` and write the current UTC timestamp.
3. Detect the OS as `windows`, `macos`, or `linux`. For each object in the manifest from Preconditions `envChecks`, in order, record step `3.1`, `3.2`, and so on. Apply the version rules in Verify. `node --version` uses the Node.js rule. A `Minimum:` that does not start with a digit passes on `expected` alone, except `node scripts/android-sdk-platform.mjs`, which passes when it prints `android-sdk-` plus any installed API level. When the OS is not `macos` and both `install.windows` and `install.linux` start with `macOS only:`, record that check `skipped`. Otherwise run `command`, read stdout and stderr together, and record `done` or `blocked`. For a blocked check, print `fail`, the command, and the `install` hint for this OS. Do not run the hint in this step. Write each timestamp, then set step `3` to `done` or `blocked`.
4. Set the command status to `done` when step `3` is `done`, otherwise `blocked`, and write the timestamp. If any check is `blocked` and `answers.runInstallHints` is missing, ask once whether to run the install hints and record `yes` or `no`. Do not ask when that answer is already set. When it is `yes`, run each failed hint once, then repeat those checks and write the new statuses. When it is `no`, leave the command `blocked`. A hint that starts with `macOS only:` is not an installer.

## Verify

The report lists every `envChecks` entry as pass, fail, or skipped. A pass means `expected` appears in the combined stdout and stderr and the reported version satisfies that entry's `Minimum:`. The Android SDK platform check is the exception: it passes when the script prints `android-sdk-` plus any installed API level, including a level other than the one in `expected`. Windows and Linux hints that start with `macOS only:` are skipped when the OS is not macOS. The command is `done` only when every entry passed or was skipped. Each failure includes the install hint for the current OS. When any check failed, `answers.runInstallHints` is `yes` or `no`. When every check passed or was skipped, that key is absent. The transcript and state file contain no values from `.env` or other secrets.

Version rules:

- Node.js passes on `22` when the minor is at least `13`, on `24` when the minor is at least `3`, and on even majors `26` or newer. Odd majors fail.
- A single `Minimum:` version passes when each numeric part is greater, or earlier parts are equal and the first differing part is greater. A shorter version is padded with zeros.
- JDK passes when the major is at least the minimum. For a quoted version starting with `1.`, the major is the second component. Otherwise it is the first.
- `java -version` writes to stderr. Read stdout and stderr together.
- The Android SDK platform check passes when the command prints `android-sdk-` plus an installed API level. The script searches installed platforms and prints the requested level when that platform is installed. Otherwise it prints the newest installed level above the request, or the newest installed level when only an older platform is present. `missing` fails only when no platform is installed. Do not block the command because the printed level differs from `expected`.

## Rollback

Set `commands.env-check.status` to `blocked` and timestamp it. Do not uninstall tools. Leave application files untouched so the failed checks can be resumed.

## Never

Do not install, upgrade, or remove a toolchain unless the developer explicitly says yes after the failed checks and their install hints are on screen. Do not treat a missing Xcode install on Windows or Linux as a pass.

## Goal

Recommend one monetization model and record it so a later paywall can gate the premium features.

Ask the four questions in Ask in one batch, then write `docs/monetization.md` and the recommendation into `.shipkit/state.json` `answers`. The model is one of `free`, `freemium`, `trial`, `subscription`, or `one-time`.

Choose it from the answers:

- `free` when the app has no paid value and no ongoing cost to recover.
- `one-time` when the app is a finished tool and `runCost` is `none` or trivial.
- `subscription` when hosting, AI, content, or another cost continues after install.
- `freemium` when a useful core can stay free and a costly or advanced slice is paid. Use a subscription for that slice when the cost continues, or a one-time product when it does not.
- `trial` when the value shows up only after use. The trial is an introductory offer on the subscription, with the same entitlement.

Say which answers led to that model.

The document also has a feature-gating table, suggested prices, regional pricing notes for low-income markets in the country mix, and one entitlement name. Suggested prices are for the store console. The app reads the store's localized price at runtime.

## Preconditions

- `.shipkit/state.json` exists and `platform` is `flutter`.
- `docs/billing-setup.md` exists. Regional price notes for Google Play come from that file.
- Run every command from the repository root.

| `appPurpose` | What does the app do? | Non-empty string. |
| `runCost` | What is costly to keep running? | String. Use `none` when nothing is. |

### Manual steps

Live Play products and the Play-to-RevenueCat service account need an app that already exists in Play Console. Show this block only when `storeTargets` includes `play`. The citations are in `docs/billing-setup.md`, checked on 2026-10-20.

- Play billing features, including configuring products, stay unavailable until a version of the app that includes the Play Billing Library is published to a track. Internal testing counts. [Getting ready](https://developer.android.com/google/play/billing/getting-ready) says to create the app and publish to any track, including the internal test track.
- An in-app product is created inside that app at Monetize with Play > Products > In-app products. Product IDs are permanent. [Create an in-app product](https://support.google.com/googleplay/android-developer/answer/1153481) is the Play Console Help page.
- RevenueCat's [Google Play Service Credentials](https://www.revenuecat.com/docs/service-credentials/creating-play-service-credentials) lists "Your app created in Google Play Console" as a prerequisite. The next step adds that existing app under the service account's App permissions. New credentials can take up to 36 hours to work.

If `answers.allowLiveStoreProducts` is not `yes`, do not create those products and do not link the service account.

## Verify

The paywall reads the current offering's packages and displays each package's store price string. It does not contain a hard-coded amount. Loading, error, and empty offerings each render their own state. Restore purchases is wired to a Restore control and is not called on launch.

## Goal

Compare `.shipkit/state.json` `kitVersion` with the latest release notes, then apply each guide in `docs/migrations/<version>.md` between those versions. `<version>` is `major.minor.patch`.

In this repository the release notes are `CHANGELOG.md` and the latest version comes from `package.json` `version`, or a higher version heading in the changelog. In an app created by `createshipyard`, the release notes are `docs/kit/CHANGELOG.md` and the synced version is `docs/kit/version.json`. To move an app to a newer kit checkout, replace only those two files and `docs/migrations` from that checkout. Do not copy feature code while refreshing them.

`node scripts/plan-update.mjs` prints the plan as JSON. It does not edit files.

## Preconditions

- `.shipkit/state.json` exists and `platform` is `flutter`.
- The current directory is the project root: this kit repository, or an app created by `createshipyard`.
- `node scripts/plan-update.mjs` runs from that root. In the kit it reads `CHANGELOG.md` and `package.json`. In a generated app it reads `docs/kit/CHANGELOG.md` and `docs/kit/version.json`. Guides are `docs/migrations/<version>.md`.
- The directory is a git checkout. `git rev-parse --is-inside-work-tree` prints `true`.

## Ask

Run `node scripts/plan-update.mjs` before asking. Do not edit files while asking. If the script fails because `.shipkit/state.json` is missing, stop and tell the developer to run `createshipyard` or `/ship-start` first.

When `migrations` is empty, or `ahead` is true, ask nothing.

When `migrations` lists one or more versions, ask once. Show the version list and each `docs/migrations/<version>.md` path before asking.

| Id | Question | Record |
| --- | --- | --- |
| `applyUpdates` | Apply these kit migrations, in order? | `yes` or `no`. |

On resume, reuse `answers.applyUpdates` and do not ask again.

## Steps

1. Run `node scripts/plan-update.mjs`. If it exits non-zero, set `commands.update.status` to `blocked`, timestamp it, and stop. If `commands.update.status` is `done`, `ahead` is false, and `kitVersion` equals `latest`, report that the project is already on that kit version and stop. Otherwise record step `1` as `done` and keep the JSON for the later steps.
2. If `ahead` is true, set `commands.update.status` to `skipped`, leave `kitVersion` unchanged, tell the developer the recorded version is newer than the release notes, and stop. If `migrations` is empty, set `kitVersion` to `latest` when it differs, set `commands.update.status` to `done`, write the UTC timestamp, report that no migration guides apply, and stop. Otherwise record step `2` as `done`.
3. If `answers.applyUpdates` is not `yes`, set `commands.update.status` to `skipped`, leave `kitVersion` unchanged, and stop. Otherwise set `commands.update` and step `3` to `in_progress`, write the UTC timestamp, and record step `3` as `done`.
4. Take a git checkpoint before editing. Let `<stamp>` be the current UTC time in compact form, such as `20261021T120000Z`. Run `git rev-parse HEAD` and `git branch ship-update-checkpoint-<stamp> HEAD`. If `git status --porcelain` is not empty, run `git stash push --include-untracked -m ship-update-checkpoint-<stamp>` and remember that a stash was created. Write `.shipkit/update-checkpoint.json` as two-space JSON with `branch`, `head`, and `stashed` (`true` or `false`). Record step `4` as `done`. If the branch cannot be created, record step `4` as `blocked`, set `commands.update.status` to `blocked`, and stop.
5. Apply each version in `migrations` in order. Open `docs/migrations/<version>.md`. Edit only paths named in that guide. Do not edit Dart files under `lib` that the guide does not name. Do not reformat an unnamed file. After each guide, check the result it describes. If a guide has no separate check, read the paths it names and confirm those edits are present. On a failure, record step `5` as `blocked`, set `commands.update.status` to `blocked`, and stop without bumping `kitVersion`. When every guide has been applied, record step `5` as `done`.
6. Set `kitVersion` to `latest`. Set `commands.update.status` to `done` and write the UTC timestamp. Leave the checkpoint branch in place.

## Verify

`node scripts/plan-update.mjs` exits 0. When `ahead` is true, or `answers.applyUpdates` is `no`, `commands.update.status` is `skipped` and `kitVersion` is unchanged. A `yes` run leaves the `ship-update-checkpoint-*` branch from `.shipkit/update-checkpoint.json` pointing at the pre-update commit. Files a migration guide does not name are unchanged, including feature code the developer owns. The state file and the transcript contain no secrets.

## Rollback

Read `.shipkit/update-checkpoint.json`. If it is missing, set `commands.update.status` to `blocked`, timestamp it, and stop. Run `git reset --hard` on the recorded `head`. Delete untracked files that step 5 created and that `git status --porcelain` still shows. Do not delete files the developer had before the checkpoint, and do not `git clean` the whole tree. If `stashed` is `true`, run `git stash pop`. Set `commands.update.status` to `blocked` and timestamp it. Leave the checkpoint branch until the developer deletes it.

## Never

Do not edit a file a migration guide does not name. Do not reformat or regenerate feature code the developer owns. Do not delete the checkpoint branch as part of a successful run. Do not bump `kitVersion` when a guide failed, `ahead` is true, or the developer answered `no`. Do not install, upgrade, or remove a toolchain. Do not create accounts, spend money, upload a binary, submit to a store, or publish a package. Do not print `.env` or secret files. Do not mark update `done` while a listed migration was not applied.
